# 任务级安全执行：设计与验收

## 范围与原则

本版只给交互式 `/task start --sandbox <需求>` 增加**显式选择**的 Docker 执行模式。原有 `/task start`、普通对话和 `-p` 不改变行为。安全模式将任务内 Shell 与自动验证放进同一个本地 Linux Docker 执行器；文件工具仍由 Workspace 限制在 Worktree 内。任务 MCP 工具和宿主机 Hooks 禁用。容器只降低风险，不是对不可信镜像或 Docker daemon 的绝对隔离。

运行前必须设置 `CORECODER_SANDBOX_IMAGE`，指向用户信任且已经存在于本机的 Linux 镜像。镜像引用必须符合受限字符格式，不能以命令选项形式注入 Docker CLI。预检查要求本地 Docker context、运行中的 Linux 引擎及本地镜像；不自动拉镜像，也不在失败时回退宿主 Shell。任务元数据保存镜像名，重启恢复时再次预检查。模型 API 调用留在宿主进程，容器不继承宿主环境变量；但 Worktree 内的文件与镜像自身内置变量仍可被容器读取。

容器参数：仅以读写方式挂载任务 Worktree 到 `/workspace`，`--network=none`、`--read-only`、临时 `/tmp`、`--cap-drop=ALL`、`no-new-privileges`、非 root 用户、CPU/内存/PID 限额、`--pull=never`。每次 Shell 调用重新请求许可，不保存“始终允许”。验证脚本按原逻辑展示并确认，Linux 命令在容器中执行。轨迹仅记录授权结果及白名单原因，不记命令和参数。

## 验收矩阵

| 类别 | 用例 | 预期 |
| --- | --- | --- |
| 启动失败关闭 | 缺镜像、缺 Docker、远程 Docker context/host | 启动前报错，不创建任务 Worktree，不回退宿主执行 |
| 授权 | 对同一种 Shell 工具选“始终允许”、允许一次、拒绝 | 前者拒绝持久授权；每次命令重新确认；原因进入轨迹白名单 |
| 工具边界 | 安全模式中的 MCP、Hooks、子 Agent | MCP/宿主 Hooks 不启用；子 Agent 继承同一受限工具和许可 |
| 路径 | Shell 工作目录、验证绝对路径、符号链接 | 只接受 Worktree 内工作目录和可映射路径；目录外路径拒绝 |
| 进程 | 命令超时、Ctrl+C 中断、Docker 运行时故障 | 超时或中断强制移除本次命名容器；Docker 故障归类为环境问题，不进入代码修复循环 |
| 隔离 | 宿主环境变量、容器根目录、Worktree | 测试密钥不在容器环境；容器根目录不可写；Worktree 可按授权修改 |
| 验证 | 模拟模型完成编辑，自动验证 | 验证在 Docker 中运行，通过后绑定当前 diff；原仓库不变 |
| 回归 | 全量单元测试 | 普通模式、旧任务与评测行为不回归 |

## 执行方式与本次实测

在 CoreCoder 项目根目录，常规无网络测试（Docker 用例自动跳过）：

```powershell
$env:PYTHON_DOTENV_DISABLED='1'
python -m pytest -q tests/test_task_sandbox.py
python -m pytest -q
```

本地 Docker 验收（需 Docker Desktop 的 Linux 引擎和已构建的可信镜像；这里复用本机 `corecoder-eval:local`）：

```powershell
$env:CORECODER_SANDBOX_IMAGE='corecoder-eval:local'
python -m pytest -q tests/test_task_sandbox.py
```

2026-11-16 实测：专项安全测试 **14/14 通过**，其中两项使用真实本地 Docker：一项验证工作区写入、宿主测试密钥不透传、根文件系统只读和容器内验证；另一项以模拟模型完成“读取—编辑—自动验证—丢弃”任务闭环，原 Git 项目保持不变。其余专项用例覆盖无 Docker 时拒绝启动、镜像名校验、远程 Docker 拒绝、每次授权、超时/中断清理、MCP/Hook 禁用、环境故障分类和 Linux 验证命令选择。Docker 预检查的本机 context 为 `npipe:////./pipe/dockerDesktopLinuxEngine`，本地镜像为 `corecoder-eval:local`。完整回归 **306 通过、4 跳过**，其中两项因未设置 Docker 镜像而跳过，且这两项已在专项运行中通过。文档与源码行数一致性检查也包含在全量回归内；`git diff --check` 通过。

本次**没有调用真实模型 API**；使用模拟模型是为了把 Docker 执行与权限边界作为确定性测试。后续若做真实 API 手工验收，应在独立临时 Git 仓库中仅开放固定数据文件的修改权限，确认 `/task diff`、验证结果和轨迹后丢弃任务并核对原仓库未变化；不可把单次真实 API 成功当成安全证明。

## 尚未覆盖与限制

- 容器内的 `git` 可能无法解析 Worktree 指向宿主机的 `.git` 指针；项目可用 `/task diff` 在宿主审查补丁。镜像必须预装项目依赖；网络关闭时无法临时安装依赖。Windows `.bat` 验证脚本不适用于 Linux 容器。
- Docker daemon、镜像及镜像内置环境必须由用户信任；容器可以读取 Worktree 内的任何文件。外部系统及强对抗场景仍需更强隔离与独立安全审计。
- 本次两项真实 Docker 用例只证明受测路径能运行，尚不能给出大规模恶意命令拦截率、正常任务误拦截率或跨语言项目兼容率。后续应在多仓库、多镜像数据集上重复测量。
