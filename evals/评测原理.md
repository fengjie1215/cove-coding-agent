# 评测原理与指标

## 一次运行如何判定

运行器创建临时 Git 项目（提交身份与时间固定，A/B 起始提交一致）→ 以原有 `TaskManager` 创建 Worktree → 让 `Agent` 修改 → 检查改动是否只在允许的实现文件 → 触发原有自动验证／最多两轮修复 → 正常应用到**临时原仓库** → 在 Worktree 外执行隐藏检查。只有「验证结果仍对应当前 diff、正常应用成功、隐藏检查通过」同时成立，`success` 才为真。`--force` 不参与评测。

公开验证只证明模型通过了可见检查；隐藏测试针对边界行为，防止把「验证通过」误认为「任务真正完成」。隐藏检查分为「常规要求」和「记忆边界」两组，后者检验预置记忆提供的附加细节；两组都通过才计端到端成功。基础组未获知记忆细节，因此必须同时报告两组分数，不能将记忆边界失败直接称为普通功能错误。隐藏测试文件不复制到临时仓库，参考实现也不复制进去。每题先做原版失败／参考版通过的双向校准。

## 对照与统计

`baseline` 和 `personalized` 使用同一 CoreCoder 代码、同一题目初始版本和同一模型。B 组只增加临时私有规则与评测者预置的一条相关项目记忆；两组都不接触用户真实 `~/.corecoder`。按 `(case, repeat)` 配对，报告端到端成功率及百分点差，并分列公开验证、正常应用、隐藏测试、耗时、模型调用次数、修复轮数和 token。若提供方不返回 token 用量，记录为 `null`，不能解释为零。预置记忆含有与边界条件相关的信息，因此此对照衡量「相关已知记忆被提供时」的效果，不能外推为自动学习系统的整体收益。

12 题是小规模自建集，重复运行可以观察波动，却不足以证明一般化性能优势。不得只挑成功样例、把模拟模型结果当成真实成绩，或把两组不同模型／不同工具权限的运行直接对比。

## 数据与风险

JSONL 只记录结构化状态、工具名、写入／编辑的结果类别、停止原因、越界尝试计数、用例 ID、计数和哈希，不保存工具参数内容、API Key、完整对话、原始 Shell 输出或完整 diff。结果文件默认 Git 忽略。评测 Agent 没有 Shell 与 MCP 工具，系统提示明确由任务控制器执行验证；非目标写入在工具边界即时拒绝，最终 Git diff 仍复核。轮数或预算耗尽标为未完成。验证会执行模型写出的 Python，仍可能造成 Worktree 外副作用；真实 API 批量运行必须在一次性容器／虚拟机中进行。自动清理的临时目录不可用作唯一审计记录，失败分析应以脱敏 JSONL 和人工复核为准。

方法论参考 [OpenAI Docs：Evaluate agent workflows](https://developers.openai.com/api/docs/guides/agent-evals) 对执行轨迹、可重复数据集与评测运行的区分；这里采用本地、提供商无关的实现，不调用 OpenAI 评测平台。
