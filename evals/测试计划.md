# CoreCoder 评测测试计划

## 目标与范围

评估现有 CoreCoder 完成小型 Python 编码任务的端到端可靠性，并在同一版本、同一模型和相同工具权限下比较「关闭个性化」与「启用项目规则及已确认记忆」。本阶段不评估 Java 感知，也不把这套自建用例当作通用 Coding Agent 排名。

## 测试集

- `cases.json` 固定 12 题：`numbers`、`strings`、`records` 三个自建项目，各四题；覆盖修 Bug、补功能和边界条件。
- 每题从相同的夹具文件生成新的临时 Git 仓库与固定初始提交。公开验证用 `unittest` 跑该题的可见测试；`hidden_tests/check.py` 位于任务 Worktree 外，仅在应用后判定。
- `golden/` 只用于评测集校准和模拟模型自检，不进入 Agent 工作区。每题必须满足：原始版本公开与隐藏检查失败，参考版本两者通过。

## 对照设计

- A / `baseline`：临时规则目录和记忆库为空。
- B / `personalized`：同一任务额外注入一条私有项目规则及一条由评测者预置的项目记忆。它模拟「已经审核并可检索的记忆」，不测试候选生成／人工接受流程。模型、温度、上下文上限、工具和验证命令相同。
- 顺序由固定种子打乱；正式真实 API 评测每题每组重复三次，共 72 次运行。先跑每个夹具一题、两组各一次的六次试运行，确认网络、时间与费用，再决定是否执行正式批次。
- 这项 A/B 测量「有无个性化上下文」，不测「确认后学习」的自动候选质量。候选接受率与后续任务影响需另建连续任务实验，不混入首批成功率。

## 执行步骤

1. 在项目根目录运行 `python -m pytest evals/test_evals.py -q`，确认夹具校准、路径拦截、轮数／预算耗尽分类和模拟端到端测试通过。
2. 运行 `python -m evals.run --mock --pilot`；再用 `python -m evals.report evals/results/<运行文件>.jsonl` 查看自检报告。自检不调用 API。
3. 在一次性容器或虚拟机中配置与日常 CoreCoder 相同的模型 API 环境，运行 `python -m evals.run --live --allow-code-execution --pilot`。先审核六次试运行结果及预计 API 开销。若要增加轮数，显式设置相同的 `--agent-rounds` 和 `--max-calls`，并把预算写入报告。
4. 若试运行无运行器异常，再运行 `python -m evals.run --live --allow-code-execution --repeats 3 --seed 1102`。如需小范围重试，用 `--case num-clamp` 或 `--mode baseline`；不得把不同批次未说明地合并。
5. 对每次 JSONL 运行 `python -m evals.report <路径>`；核对配对数、失败案例和费用后，将真实结果摘要写入 `测试结果.md`。

若 `python` 不在 PATH，以上命令可改用当前已安装 `pytest` 与 CoreCoder 的 Python 解释器绝对路径。真实运行会从当前项目的 `.env` 或环境变量读取模型配置；不要把密钥写入用例或报告。

## 运行边界

Agent 仅获文件读写、编辑、搜索及 Todo 工具；不提供 Shell、外部 MCP、子 Agent 或 Hooks。系统提示说明验证由任务控制器负责，修改范围限题目对应实现文件；其他写入在工具边界即时拒绝并记数，自动验证前再用 Git diff 复核。每次运行的任务、规则和 SQLite 记忆都位于独立临时目录，默认退出后清除。模型调用数、Agent 单次对话轮数、可观测 token 数与调用前时间上限可通过命令参数限制；单次网络请求和验证进程另有各自超时，这不是整个宿主机的硬安全边界。
